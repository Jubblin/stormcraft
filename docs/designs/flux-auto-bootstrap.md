# Design: Fully declarative bootstrap — Omni sync through Flux reconciliation

## Problem Statement

Getting from an empty Proxmox host to a running cluster with Flux actively
reconciling `clusters/stormcraft/` today needs three separate categories of
by-hand steps, spread across two READMEs:

1. Manually run `omnictl cluster template sync` (Omni build path).
2. Manually re-trigger `kubectl apply -k cilium/` / `flux-operator/` if the
   Talos inlineManifest race is missed (documented fallback, not automatic).
3. Manually `kubectl create secret generic git ...` with a real credential,
   then `kubectl apply -f flux-operator/instance.yaml` — this step can't be
   an inlineManifest at all today, since the `FluxInstance` CRD doesn't
   exist until flux-operator's Helm chart installs it, and the secret needs
   a real credential a human has to type in.

No single command exists that goes from "nothing" to "Flux reconciling."

## What Makes This Cool

Rebuild the cluster from scratch, add a 4th worker, whatever — the same
declarative chain reproduces itself with **only one manual secret ever**
(an `age` private key, not the git deploy key), using the same Talos
inlineManifests mechanism that already self-heals Cilium and
flux-operator today. Near-term (option a below) that key gets
`kubectl create`'d once per cluster rebuild; the follow-up (option b)
removes even that.

## Constraints

- Homelab, not commercial — optimize for "works reliably, fun to build,"
  not multi-tenant or support burden.
- Secrets must never be committed in plaintext.
- Must stay compatible with the existing `flux-operator/job.yaml` Job
  pattern (cluster-admin ServiceAccount, `ttlSecondsAfterFinished`, no
  CNI-bootstrap hacks needed once Cilium is up).

## Premises

1. **Idempotent, resumable** — re-running the chain after a partial
   failure (e.g. missed the Cilium 10-minute window) picks up where it
   left off. *Agreed.*
2. **Flux takes over after bootstrap** — once `FluxInstance` is Ready,
   Agones/GameServer manifests and everything else land under
   `clusters/stormcraft/` and get reconciled by Flux, not `kubectl
   apply`'d by a script. *Agreed.*
3. **Local trigger vs. CI trigger** — left open. See Open Questions.

## Approaches Considered

### Approach A: One bootstrap.sh script
Chain `omnictl cluster template sync` → wait for nodes Ready → wait for
Cilium/flux-operator Jobs → apply `FluxInstance` → wait Ready, in one
idempotent script. Git secret still created by hand once. Effort: S.
Completeness: 8/10 — covers the whole chain, leaves secret provisioning
manual on purpose.

### Approach B: Fully declarative via SOPS + Talos inlineManifests (chosen)
Encrypt the git deploy key with SOPS/age, commit it, add a
retry-until-CRD-exists Job so `FluxInstance` applies itself as an
inlineManifest alongside Cilium/flux-operator. Zero manual `kubectl` after
`talosctl bootstrap` / Omni sync. Effort: M. Completeness: 10/10.

### Approach C: GitHub Actions pipeline
Push-to-main triggers a self-hosted-runner workflow running the same
chain, for reproducibility/audit trail. Needs a self-hosted runner
reachable from the home Proxmox network plus repo secrets. Effort: L.
Rejected — disproportionate infra for a homelab project; no one else is
merging to this repo who'd benefit from CI-triggered reproducibility.

## Recommended Approach

**B.** It closes the gap completely (no more "manual re-trigger" caveats
in either README) and reuses a mechanism the repo already trusts — Talos
inlineManifests self-healing Cilium and flux-operator. It also means a
full cluster teardown/rebuild (something a homelab setup will hit more
often than a production one) never requires remembering a sequence of
manual commands again.

### Implementation sketch

1. `.sops.yaml` + a generated `age` keypair. Private key lives in a
   password manager / `~/.config/sops/age/keys.txt` — **never committed**.
2. `flux-operator/git-secret.enc.yaml` — a SOPS-encrypted Kubernetes
   `Secret` manifest holding the git PAT (the same `username`/`password`
   shape as today's manual `kubectl create secret generic git` command in
   talos/README.md step 7). Committed encrypted.
3. A decrypt-and-apply Job (same `alpine/k8s`-based pattern as
   `flux-operator/job.yaml`, with `sops` and `age` installed via `apk add`
   in the Job's `command` — no new base image needed, matching
   `ttlSecondsAfterFinished` cleanup): decrypts `git-secret.enc.yaml`,
   applies it to `flux-system`. Needs the `age` private key on-cluster as
   a pre-existing `Secret` — see Open Questions for where that one
   remaining secret lives long-term. Scoped to a namespace-local
   `Role`/`RoleBinding` in `flux-system` (get/create/update on secrets
   only) — **not** cluster-admin like `flux-operator/job.yaml`'s Helm
   install, which genuinely needs cluster-admin for CRDs/ClusterRoles;
   this Job only ever touches Secrets in one namespace.
   **Namespace-race fix:** must also retry on "namespace not found," not
   just decrypt failure — `flux-system` is created by flux-operator's own
   inlineManifest Job, and there's no ordering guarantee between
   inlineManifests applied in the same Talos pass. Retries every ~10s,
   **bounded** (`activeDeadlineSeconds`, e.g. 15 min) — if the age-key
   `Secret` is genuinely never created, the Job fails loudly instead of
   sitting Pending forever, visible via `kubectl -n flux-system get jobs`.
4. A retry-loop Job (same bounded-retry behavior, cluster-admin — this
   one's blast radius is inherent, it's applying a cluster-wide
   `FluxInstance` CR by design) that polls `kubectl get crd
   fluxinstances.fluxcd.controlplane.io` until it exists (i.e.
   flux-operator's Helm install finished), then applies
   `flux-operator/instance.yaml`.
5. Both Jobs' retry-loop shell logic (poll condition, sleep, bounded
   timeout) lives in one shared `ConfigMap`-mounted `retry-until.sh`
   script rather than duplicated inline in each Job — one place to fix
   the retry logic if it has a bug, reused by both.
6. Both Jobs added to `patches/cni-kubeproxy.yaml`'s `inlineManifests`,
   after flux-operator's own Job. Talos applies all inlineManifests in
   one pass; ordering is handled by each Job's own retry loop internally,
   the same way Cilium's preflight check and flux-operator's
   Pending-until-Ready already coexist.

## Open Questions

- **Trigger:** local one-shot command (`omnictl cluster template sync`
  run by hand) vs. something that also drives the Omni sync step itself.
  Approach B only covers the *post-cluster-exists* chain — Omni sync is
  still a manual step either way, and that's fine per the "having fun /
  homelab" goal, but worth being explicit that B doesn't fully answer
  "auto deploy a cluster."
- **Where does the `age` private key live long-term?** Options: (a) a
  one-time `kubectl create secret` per cluster rebuild — same manual step
  as today, just narrower (a meta-secret, not the Flux deploy key
  itself); (b) baked into a Talos machine config patch so it survives
  cluster rebuilds without any manual step at all. (b) is the "zero
  manual commands ever" version but adds machine-config secret handling
  to the Omni/talosctl paths — worth a follow-up design once (a) is
  proven out.

## Success Criteria

- `talosctl bootstrap` (or Omni sync completing) to `FluxInstance` Ready,
  with the only manual step being the one-time `age`-key `Secret`
  creation (option a) — or truly zero manual steps once option (b) lands.
- A full cluster teardown + rebuild reproduces the same end state without
  reconsulting either README's manual-step sections (beyond re-creating
  the age-key secret, until option b lands).
- No secret ever appears in plaintext in git history.
